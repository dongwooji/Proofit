# 1. 프로젝트 개요

## 1.1 프로젝트 소개

Proofit은 여러 채용 데이터 출처에서 채용공고를 **자동으로 발견·수집**하고, 지원자의 학력·경력·프로젝트·연구 성과를 **증거(evidence)** 단위로 관리하여 직무 적합성을 분석하는 **AI Agent 기반 개인화 취업 관리 시스템**이다.

기존 채용 플랫폼이 공고 검색과 지원에 집중하는 것과 달리, Proofit은 채용공고와 지원자의 실제 역량 사이의 관계를 분석하여 다음 질문에 답하는 것을 목표로 한다.

> "이 채용공고는 나에게 지원할 가치가 있는가? 지원 자격이 되는가? 내가 충족하는 요구사항과 부족한 역량은 무엇이며, 어떤 경험을 강조해야 하는가?"

이를 위해 AI Agent, Model Context Protocol(MCP), 버전 관리되는 증거 데이터, 결정론적 점수 계산을 결합한다. 채용공고 수집부터 적합성 평가, 이력서·자기소개서 초안 작성, 지원 현황 관리까지 하나의 시스템에서 수행한다.

## 1.2 개발 동기

1. **채용공고 분산**: 사람인, 잡코리아, 원티드, LinkedIn 등 여러 사이트를 반복적으로 방문해야 한다.
2. **공고를 찾는 노동**: 원하는 공고를 찾기 위해 매일 검색하고 링크를 모으는 일 자체가 큰 비용이다.
3. **중복 공고**: 같은 공고가 여러 플랫폼에 게시되어 중복 확인이 발생한다.
4. **주관적인 지원 판단**: 실제 경험과 공고 요구사항을 체계적으로 비교하기 어렵다.
5. **신입 지원 자격의 모호성**: 필수 경력과 우대 경력이 섞여 있어 지원 가능 여부를 판단하기 어렵다.
6. **지원자료 작성의 반복**: 같은 경험을 기업·직무에 맞게 반복해서 다시 쓴다.
7. **취업 기록의 파편화**: 지원 현황, 평가 근거, 제출 자료, 전형 결과를 통합 관리하기 어렵다.
8. **AI 평가의 불투명성**: LLM 평가는 점수 근거와 재현성을 확인하기 어렵다.

## 1.3 프로젝트 목표

**핵심 목표**

- 허용된 출처에서 신규 채용공고를 **사용자의 반복 작업 없이** 주기적으로 자동 수집한다.
- 공고를 공통 구조로 정규화하고 플랫폼 간 중복을 제거한다.
- 신입·인턴·채용연계형·경력무관 지원 가능 여부를 판단한다.
- 공고 요구사항과 지원자의 실제 증거를 연결한다.
- **Eligibility, Evidence-based Fit Score, Global Opportunity Score**를 서로 독립적으로 제공한다.
- 실제 증거만 사용해 이력서·자기소개서 초안을 만든다.
- 지원 현황과 평가 결과를 통합 관리한다.
- 평가 근거와 변경 이력을 추적해 AI 판단을 검증할 수 있게 한다.

**부가 목표**

AI Agent, MCP, 백엔드, 데이터 파이프라인, LLM 평가·검증 기술을 실제 문제에 적용하고, **정량 실험으로 설계 선택을 설명**할 수 있는 AI Engineering 포트폴리오를 만든다.

# 2. 대상 사용자 및 활용 시나리오

## 2.1 주요 사용자

초기에는 취업 준비생 한 명을 위한 **Single-user 시스템**으로 개발한다.

| 직무 분야 | 세부 대상 |
|---|---|
| AI Engineering | AI Engineer, ML Engineer, LLM Engineer |
| AI Agent | AI Agent Engineer, RAG Engineer, Applied AI |
| AI Transformation | AX, AI 컨설팅, AI 솔루션 |
| 기술영업 | Technical Sales, Sales Engineer, Presales |
| 해외영업 | Overseas Sales, Global Business Development |

**신입·인턴·채용연계형 인턴·경력무관** 포지션을 중심으로 하되, 경력직 사용자도 쓸 수 있도록 데이터 구조를 설계한다.

## 2.2 대표 시나리오

**A — 신규 공고 자동 발견**
사용자는 채용사이트를 직접 확인하지 않는다. 처음에 API 키 발급, 관심 기업 목록, 사이트별 맞춤 공고 알림을 **한 번만 설정**하면, 시스템이 정해진 일정에 따라 공고를 수집하고 중복을 제거해 대시보드의 '신규 공고' 목록에 보여 준다.

**B — 지원 자격 판단**
AI Engineer 공고를 선택하면 필수 경력, 우대 경력, 학력 조건, 고용형태를 구분해 `ELIGIBLE / INELIGIBLE / UNCERTAIN`으로 판단한다. '경력 3년 필수'와 '경력 3년 우대'는 서로 다른 조건으로 처리한다.

**C — 근거 기반 적합성 평가**
AI Agent가 공고의 요구사항을 추출하고 지원자의 이력, 연구, 프로젝트, 논문 증거와 연결한다. 규칙 기반 Scoring Engine이 Fit Score를 계산하고, 별도로 Global Opportunity Score를 제시한다.

**D — 맞춤형 지원자료 작성**
지원하기로 한 공고에 대해 관련 경험을 골라 이력서·자기소개서 초안을 만든다. 모든 성과와 수치는 등록된 증거에서만 가져오며, 근거 없는 경험을 만들지 않는다.

**E — 지원 현황 추적**
지원 예정, 지원 완료, 인적성검사, 면접, 불합격 등 상태를 바꾸면 시스템이 상태 변경 이력과 각 지원 건의 평가·제출 자료를 보존한다.

# 3. MVP 기능 명세

## F01. 사용자 프로필 및 증거 관리

**목적**: AI 평가와 문서 생성에 쓸 신뢰 가능한 후보자 데이터베이스 구축

- 기본 프로필, 기본 이력서 등록·수정
- 학력·경력·자격증·기술 역량 관리
- 프로젝트·논문·연구 경험 등록 (역할, 기술 스택, 성과 수치)
- 원본 자료와 증거 출처 연결
- 직무별 강조할 경험 설정
- **증거 버전 관리**: 수정할 때마다 새 버전을 만들고, 평가는 특정 버전을 참조

**설계 원칙**: 하나의 프로젝트에 여러 증거를 연결한다. 예를 들어 Agentic RAG 프로젝트의 'Hybrid Recall@10 개선'은 프로젝트와 별개의 구체적인 증거로 관리한다.

## F02. 채용공고 자동 수집

**목적**: 사용자가 공고를 찾아다니지 않아도 되도록, 허용된 출처에서 신규 공고를 주기적으로 수집

### 수집 경로 (Provider 유형)

| 유형 | 출처 예시 | 비고 |
|---|---|---|
| `ApiProvider` | 로켓펀치, 사람인, 고용24, (원티드) | 공식 API. 키 발급·승인 필요 여부는 출처마다 다름 |
| `AtsBoardProvider` | Greenhouse, Lever, Ashby 공개 Job Board API | 관심 기업 목록을 한 번 등록하면 자동 확인. 외국계 기업에 유용 |
| `FeedProvider` | 인디스워크 RSS 등 공식 피드 | 사이트가 공개로 제공하는 피드만 사용 |
| `EmailAlertProvider` | 잡코리아·캐치·LinkedIn 등의 맞춤 공고 알림 메일 | 사용자가 설정한 알림 메일을 읽기 전용 메일 접근으로 수집. API가 없는 사이트를 위한 핵심 경로 |
| 수동 등록 (fallback) | URL 등록, 본문 붙여넣기 | 자동 경로가 못 잡은 공고를 위한 **대체 수단** |

- **Google Alerts는 사용하지 않는다.**
- 이용약관이나 robots.txt가 자동 수집을 금지하는 채용 플랫폼(잡코리아, 캐치, 인크루트 등)은 크롤링하지 않는다.

### 발견(Discovery)과 상세 보강(Enrichment) 분리

- 알림 메일처럼 제목·회사·링크만 있는 출처가 있으므로, 공고는 먼저 **목록 메타데이터(listing)** 상태로 등록되고 **검증된 상세 JD**는 나중에 채워질 수 있다 (`detail_status`).
- 1차 필터(직무, 신입 여부)를 통과한 공고 중 상세 JD가 없는 것은 '본문 필요'로 표시한다. 상세 확보 방식은 이용약관을 확인한 뒤 출처별로 정한다.

### 공통 기능

- 출처·원본 URL·수집 시각·불변 JD 스냅샷(해시) 기록
- 수집 실패·오류 로그 저장, 재시도
- 예약 실행 (LLM 불필요)
- 플랫폼 간 중복 식별
- 마지막 수집 이후 신규 공고 표시
- 출처별 이용 조건 반영 (호출 한도, 출처 표시 의무, 저장·보존 조건)

**MVP 완료 조건**: 허용된 자동 수집 출처를 **최소 1개** 실제로 연결하고, 예약 실행으로 신규 공고가 DB에 등록되는 것을 검증한다. 1순위 후보는 키가 즉시 발급되는 로켓펀치다.

## F03. 공고 정규화 및 지원 자격 판단 (Eligibility)

**목적**: 서로 다른 공고 형식을 공통 구조로 통합하고 지원 자격을 명확히 판단

- 기업명, 직무, 근무지역, 고용형태, 마감일 추출
- 마감일 유형 구분: 날짜 / 상시채용 / 채용 시 마감 (`deadline_type`)
- **필수(mandatory) vs 우대(preferred)** 구분 — 중요도(High/Medium/Low)와는 별개의 축
- 신입·인턴·채용연계형·경력무관·경력직 분류
- 경력 연차 조건 추출 (`경력 N년 필수` vs `경력 N년 우대`)
- 원격·하이브리드 근무 여부

### 판정 결과

| 결과 | 의미 |
|---|---|
| `ELIGIBLE` | 확인된 필수 조건을 모두 충족 |
| `INELIGIBLE` | 필수 조건 미충족이 **확인됨** (knockout) |
| `UNCERTAIN` | 정보가 부족하거나 조건이 모호함 → '확인 필요' |

- Knockout은 **필수 요건이 미충족으로 확인된 경우에만** 적용한다. 증거가 없다는 것만으로는 `INELIGIBLE`이 아니라 `UNCERTAIN`이다.
- AI는 추정만으로 `UNCERTAIN`을 `INELIGIBLE`로 바꿀 수 없다.
- Eligibility는 **추천 여부를 거르는 데만** 쓰이고, **Fit Score를 바꾸지 않는다.**

## F04. 평가 — 세 가지 독립 결과

**목적**: 지원 자격, 기술적 적합성, 지원 가치를 분리해서 평가

| 결과 | 범위 | 산출 방식 | 질문 |
|---|---|---|---|
| Eligibility | 3단계 | 규칙 + AI 추출 | 지원할 수 있는가? |
| Evidence-based Fit Score | 0~100 | 결정론적 Python 계산 | 요구사항을 증거가 얼마나 충족하는가? |
| Global Opportunity Score | 1~5 | LLM 종합 판단 | 지원할 가치가 있는가? |

세 결과는 **서로 덮어쓰거나 조정하지 않는다.** 상세 설계는 4장 참고.

**Global Opportunity Score**는 진로 연관성, 보상 수준, 근무지역·근무조건, 성장 기회, 위험 요소를 항목별로 설명한다. 공고에 없는 정보는 **'미확인'**으로 표시하고 지어내지 않는다. 어떤 점수도 **합격 확률이 아니다.**

## F05. 지원 상태 관리 대시보드

**목적**: 공고 검토부터 최종 결과까지 통합 관리

**공고 상태 (`job.status`)**: `OPEN`(진행) / `CLOSED`(마감) / `UNKNOWN`(미확인)

**지원 상태 (`application.status`)**

| 상태 | 한국어 | 구분 |
|---|---|---|
| `REVIEWING` | 검토 | 진행 |
| `PLANNED` | 지원 예정 | 진행 |
| `APPLIED` | 지원 | 진행 |
| `ASSESSMENT` | 시험 (인적성·코딩테스트 등) | 진행 |
| `INTERVIEW` | 면접 | 진행 |
| `OFFER` | 합격 | 종료 |
| `REJECTED` | 불합격 | 종료 |
| `WITHDRAWN` | 철회 | 종료 |
| `SKIPPED` | 건너뜀 (지원하지 않기로 함) | 종료 |

- 공고 마감은 지원 결과가 아니므로 지원 상태에 넣지 않는다.
- '신규 공고'는 지원 상태가 아니라 공고 쪽 속성(마지막 수집 이후 발견)으로 관리한다.
- 모든 상태 변경은 이벤트로 기록한다.

주요 기능: 기업명·직무 검색, 상태별 필터, 점수 정렬, 마감일 정렬, 지원일·결과 기록, 메모, 상태 변경 이력 조회

## F06. 맞춤형 이력서 및 자기소개서 초안

**목적**: 공고와 연결된 실제 경험으로 지원자료 작성 효율 향상

- 공고별 관련 경험 추천, 핵심 기술·성과 강조
- 이력서 초안, 한국형 자기소개서 문항별 초안
- **글자 수 검사**: 기업이 정한 기준대로 (공백 포함 / 공백 제외 / 바이트)
- **주장–증거 연결**: 초안의 각 주장(문장)이 어떤 증거 버전에 근거하는지 기록하고 검증
- 초안 수정과 버전 관리, Markdown 내보내기 (PDF는 MVP 이후)

AI는 검증 가능한 사실을 재구성할 수 있지만, **새로운 경력·성과·수치를 만들 수 없다.**

## F07. 평가 결과와 변경 이력 관리

**목적**: AI 평가의 재현성과 추적 가능성 확보

기록 대상:

- 공고 스냅샷 ID, 요구사항 세트 ID(버전)
- 평가 실행 시각
- 평가 정책(policy) 해시, Agent skill·프롬프트 해시
- **보고된(reported)** 모델 식별 정보 — Agent가 스스로 보고한 값이므로 검증된 값이 아님
- 세 가지 평가 결과
- 요구사항별 증거 연결 (증거 **버전** 참조)
- LLM 원본 판정과 사용자 확정 판정
- 재평가 전후 결과, 지원 상태 변경 이력

같은 공고의 점수가 바뀌었을 때 **공고가 바뀐 것인지, 증거가 수정된 것인지, 정책·모델이 바뀐 것인지** 구분할 수 있어야 한다.

## F08. AI Agent 및 MCP 연동

**목적**: AI가 구조화된 도구를 통해 공고와 후보자 데이터를 조회·분석

- MVP는 **Single-Agent**. 사용자가 Claude Code에서 직접 실행한다.
- MCP Server가 Claude Code와 Proofit 백엔드 사이의 인터페이스를 제공한다.
- AI 결과는 `DRAFT`로 저장되고, 사용자가 대시보드에서 검토·확정한다. 확정해도 이력은 덮어쓰지 않는다.
- 사용자가 승인하지 않은 지원서 제출, 이메일 발송은 **절대 하지 않는다.**

# 4. 평가 상세 설계

## 4.1 요구사항의 두 축

요구사항은 서로 독립적인 두 속성을 가진다.

| 축 | 값 | 용도 |
|---|---|---|
| 필수 여부 | 필수 / 우대 | Eligibility (knockout 판단) |
| 중요도 | High / Medium / Low | Fit Score 가중치 |

중요도는 **공고 자체의 표현과 구조**로 판정한다. 지원자가 그 기술을 잘하는지에 따라 중요도를 바꾸지 않는다.

## 4.2 중요도 가중치

| 등급 | 가중치 | 의미 |
|---|--:|---|
| High | 5 | 공고에서 강하게 강조된 핵심 요구사항 |
| Medium | 3 | 직무 수행에 중요한 일반 요구사항 |
| Low | 1 | 상대적으로 중요도가 낮은 요구사항 |

## 4.3 증거 강도 (Rubric)

| 등급 | 계수 | 판정 기준 |
|---|--:|---|
| Strong | 1.0 | 직접 수행이 확인됨 |
| Partial | 0.5 | 관련 경험은 있지만 요구 범위·깊이가 부족함 |
| None | 0.0 | 검토한 자료에 근거가 없음 |
| Unknown | 별도 처리 | 판단할 자료가 부족함 |

`None`과 `Unknown`은 데이터상 반드시 구분한다. 모든 판정은 근거가 된 **증거 ID(버전)**와 연결한다.

## 4.4 계산 공식

```
Fit Score = 100 × Σ(가중치 × 강도) / Σ(가중치)
```

- **하한 (lower bound)**: Unknown을 0으로 계산
- **상한 (upper bound)**: Unknown을 1.0으로 계산
- **Evidence Coverage**: 전체 가중치 중 Unknown이 아닌 판정의 가중치 비율
- 계산은 `Decimal`로 하고, **소수 첫째 자리에서 반올림(ROUND_HALF_UP)** 한다.
- 대표 점수는 하한을 쓰고, 상한과 Coverage를 함께 보여 준다.
- Coverage가 기준보다 낮으면 단일 점수로 추천하지 않고 '증거 확인 필요'로 표시한다. **기준값은 평가 데이터셋으로 검증한 뒤 정책에 고정**한다.

## 4.5 결정론적 계산의 범위와 재현성

- 같은 승인된 입력(요구사항 세트, 증거 버전, 판정)과 같은 정책 버전이면 Scoring Engine은 **항상 같은 점수**를 반환한다.
- LLM이 요구사항을 추출하거나 강도를 판정하는 과정은 확률적이다. 그래서 다음을 따로 저장한다.
  - LLM 원본 판정, 사용자 승인·수정 결과
  - 실제 Scoring Engine 입력값, 정책 버전, 최종 점수
- **요구사항 세트는 공고 스냅샷 단위로 고정**한다. 재평가할 때는 승인된 요구사항 세트를 재사용하고, JD가 바뀌었거나 추출을 명시적으로 수정했을 때만 새 버전을 만든다. 평가마다 요구사항을 다시 추출하면 분모가 흔들려 점수가 달라지기 때문이다.

FastAPI와 MCP 서버는 **같은 서비스 계층**을 사용한다. 검증, 수집, 중복 제거, 점수 계산, 저장 로직을 두 곳에 따로 두지 않는다.

```
Scheduler ─► Collectors ┘
```

## 5.3 데이터 흐름

**A. 수집 경로 (LLM 없음)**
Provider (API / ATS / RSS / 알림 메일 / 수동) → 정규화 → 중복 제거 → 스냅샷 저장 → DB → 1차 필터 → 평가 대기열

**B. 평가 경로 (사용자가 Claude Code에서 실행)**
평가 요청 → AI Agent → MCP Tools → 요구사항 세트 조회·추출 → 증거 조회 → Evidence Mapping → 구조화된 결과 → Python Scoring Engine → 검증 후 `DRAFT` 저장 → 대시보드에서 검토

**C. 지원자료 생성 경로**
평가된 공고 선택 → 관련 증거 조회 → 초안 생성 → 주장–증거 검증 → 사용자 검토·수정 → 문서 버전 저장

## 5.4 AI 실행 및 비용 정책

- MVP는 Claude Code에서 Agent를 **사용자가 직접 실행**한다.
- 수집, 정규화, 중복 제거, 상태 변경은 LLM 없이 동작한다.
- Claude Code 구독을 무인 백엔드 API 인증 수단으로 쓰지 않는다.
- 완전 자동 AI 평가가 필요해지면 별도의 정식 API 연동, 인증, 비용 한도, 실행 일정을 설계한다.

## 6.2 핵심 관계

- Candidate Profile 1 : N Projects
- Project 1 : N Evidence Items, Evidence Item 1 : N Evidence Item Versions
- Job 1 : N Job Sources, Job 1 : N Job Snapshots
- Job Snapshot 1 : N Requirement Sets, Requirement Set 1 : N Job Requirements
- Job 1 : N Evaluations, Evaluation N : 1 Requirement Set, Evaluation N : 1 Scoring Policy
- Evaluation 1 : N Evidence Matches
- Evidence Match N : 1 Job Requirement, Evidence Match N : 0..1 Evidence Item Version
- Job 1 : 0..1 Application, Application 1 : N Application Events
- Document 1 : N Document Versions, Document Version 1 : N Document Claims

## 6.3 설계상 중요한 제약

- **중복 제거**: `jobs`와 `job_sources`를 분리한다. 정규화된 URL, 플랫폼별 공고 ID, 기업명·직무명·지역으로 중복 후보를 찾고, 불확실한 중복은 `duplicate_candidates`에 남겨 사용자가 확인한다.
- **평가 이력**: 재평가는 기존 평가를 덮어쓰지 않고 새 `evaluations` 레코드를 만든다.
- **증거 추적**: 평가와 문서는 증거의 **특정 버전**을 참조한다. 증거를 수정해도 당시 판정을 복원할 수 있다.
- **상태 분리**: 공고 상태(`jobs.status`)와 지원 상태(`applications.status`)를 분리하고, 지원 상태 변경은 모두 `application_events`에 기록한다.
- **마이그레이션**: 스키마 변경은 Alembic으로 관리한다.

# 8. AI Agent 및 MCP 설계

## 8.1 Agent의 역할

Agent는 텍스트 생성기가 아니라 **평가에 필요한 정보를 골라 조회하고, 부족한 정보에 따라 다음 행동을 정하는 주체**다. 필수 요건을 확인할 수 없으면 공고 정보를 더 조회하고, 증거가 부족하면 후보자 정보를 더 찾거나 사용자에게 확인을 요청한다.

중복 제거, 가중치 계산, 상태 전이 검증은 일반 코드로 구현한다.

| Agent | Python Backend |
|---|---|
| 요구사항 해석, 필요 정보 선택, Tool 호출, 증거 연결, 불확실성 판단, 구조화된 결과 생성 | 조회·저장, 중복 제거, 스키마 검증, 점수 계산, 권한·무결성 관리 |

## 8.2 MCP 설계

**Tools**

| Tool | 유형 | 기능 |
|---|---|---|
| `search_jobs` | Read | 조건에 맞는 공고 검색 |
| `get_job_details` | Read | 공고 원문·정규화 데이터·요구사항 세트 |
| `get_candidate_profile` | Read | 후보자 프로필 (평가에 불필요한 개인정보 제외) |
| `search_candidate_evidence` | Read | 기술·프로젝트·성과 증거 검색 |
| `get_evaluation_history` | Read | 과거 평가 결과 |
| `calculate_fit_score` | Compute | 고정 정책 기반 점수 계산 |
| `save_evaluation` | Write | 평가 결과를 `DRAFT`로 저장 |
| `create_document_draft` | Write | 문서 초안을 `DRAFT`로 저장 |

**Resources**: 후보자 프로필 요약, 현재 Scoring 정책 등 읽기 전용 문맥
**Prompts**: 공고 평가 워크플로 템플릿

**원칙**
- 읽기와 쓰기 권한을 분리한다.
- 쓰기 도구에는 스키마 검증, 중복 요청 처리(idempotency key), 감사 로그를 적용한다.
- 공고 본문과 메일 내용은 **명령이 아닌 비신뢰 데이터**로 다룬다.
- 연락처 등 평가에 필요 없는 개인정보는 MCP 응답에서 제외한다.
- 평가 워크플로는 Claude Code skill 파일로 관리하고, 그 **파일 해시를 프롬프트 버전**으로 기록한다.
- Claude Code 외 다른 MCP 클라이언트에서도 같은 서버가 동작하도록 만든다.

## 8.3 멀티에이전트 확장 계획

멀티에이전트는 MVP 이후 **통제된 실험**으로 도입 여부를 정한다. 중심은 **독립 검증(Verification)**이다.

| 후보 지점 | 기대 효과 |
|---|---|
| 독립 검증 Agent (평가 Agent의 추론을 보지 않고 원본 증거만으로 재확인) | 높음 |
| 문서 작성 Agent ↔ 사실 검증 Agent | 높음 |
| 여러 공고 병렬 평가 | 중간 (처리량) |
| Research Agent | 낮음 |

**실험 설계**: 같은 평가셋에서 아래 네 가지를 비교한다.

1. 단일 Agent (기준선)
2. 단일 Agent + 같은 맥락에서 자기 검토
3. 단일 Agent + **독립된 맥락의** 검증 Agent
4. 역할을 모두 나눈 멀티에이전트

2번과 3번의 차이가 "에이전트를 나눈 효과"다. 개선이 없으면 단일 Agent를 유지한다.

**구현 순서**: Claude Code 서브에이전트로 역할·권한 분리를 먼저 실험하고(검증 Agent는 읽기 도구만), 이후 Agent SDK 또는 API로 오케스트레이션을 직접 구현한다. 이때는 5.4의 비용 정책을 따른다.

# 10. 보안 및 신뢰성

## 10.1 개인정보 보호

- 이력서, 프로젝트 자료, 지원 기록은 로컬에 저장한다.
- API 키와 인증정보는 환경변수 또는 별도 Secret 저장소로 관리하고 Git에 커밋하지 않는다. (레포의 hook이 `.env`, DB 파일, `data/` 커밋을 차단한다.)
- Claude Code로 평가하면 관련 데이터가 모델 제공자에게 전송될 수 있다. 평가에 필요 없는 개인정보는 MCP·LLM 전송 대상에서 제외한다.
- 사용자 데이터 백업과 삭제 기능을 둔다.
- 공개 레포에는 실제 개인 데이터나 수집한 공고 원문을 넣지 않는다. 데모에는 합성 데이터를 쓴다.

## 10.2 채용정보 수집 정책

- 공식 API, 공개 ATS Job Board API, 공식 RSS, 사용자가 설정한 알림 메일만 자동 수집에 쓴다.
- 로그인 우회, robots.txt·접근 제한 회피, CAPTCHA·봇 차단 우회를 구현하지 않는다.
- 출처마다 이용약관, 인증, 출처 표시, 저장·보존 조건, 호출 한도를 확인하고 지킨다.
- 원본 URL과 출처를 기록한다.
- 접근 권한이 없는 출처는 자동 수집을 비활성화한다.

## 10.3 LLM 신뢰성

- 공고 본문과 메일 내용은 비신뢰 데이터로 처리한다.
- AI 출력은 Pydantic 스키마로 검증한다.
- 근거 없는 사실 주장은 저장·사용 단계에서 표시하거나 차단한다.
- 결정론적 계산은 Python 함수로 수행한다.
- 평가 실패와 불확실성은 명시적으로 표시한다.
- AI 판단(`DRAFT`)과 사용자 확정 판단을 구분해 저장한다.

## 10.4 Human-in-the-Loop

사용자 검토가 필요한 작업: 불확실한 중복 병합, 중요한 증거 판정 수정, 요구사항 세트 승인·수정, 지원 여부 최종 결정, 최종 지원자료 사용, 외부 지원서 제출. 지원서 자동 제출 기능은 구현하지 않는다.

# 11. 평가 및 테스트 계획

## 11.1 수집 품질

- 출처별 수집 성공률, 필수 필드 추출 정확도
- 중복 식별 정확도, 마감 공고 검출 정확도
- 실패 후 재시도 동작
- **커버리지**: 다른 경로로 알게 된 공고 중 시스템이 이미 찾아 둔 비율 (출처별 기여도 포함)

## 11.2 AI 평가 품질

- 요구사항 추출 정확도, 필수·우대 분류 정확도
- **추출 안정성**: 같은 공고를 N번 추출했을 때 요구사항 수와 점수의 변동
- Eligibility 판정 정확도 (특히 잘못된 `INELIGIBLE`)
- Evidence Mapping 정확도(precision), 근거 없는 주장 발생률
- 같은 승인 입력에 대한 점수 재현성(replay consistency)
- 지연 시간, 토큰 사용량

실제 공고 30~50개를 사람이 검토한 평가 데이터셋을 만들고, 판정 기준(rubric)에 따라 라벨링한다. 정답이 불명확한 사례는 따로 분류한다.

## 11.3 기준선 비교

- **LLM 단일 종합 점수 vs 증거 기반 평가**: 사용자의 실제 판단(지원 여부, 서류 결과)과 얼마나 일치하는지 비교한다.
- 멀티에이전트 비교는 8.3의 실험 설계를 따른다.

# 12. 개발 로드맵

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1. 기반 | DB 모델, 공통 서비스 계층, Alembic 마이그레이션, CRUD, 테스트 | 공고·증거 등록·조회·수정, 상태 변경 테스트 통과 |
| 2. 자동 수집 | **실제로 자동 동작하는 허용된 출처 1개**, 예약 실행, 중복 제거, 로그, 기본 목록 | 예약 작업으로 신규 공고 수집, 재수집 시 중복 없음 |
| 3. 평가 엔진 | 스냅샷·증거 버전, Eligibility 규칙, 결정론적 점수, rubric 테스트 | 같은 입력 → 같은 점수, 점수 근거 조회 가능 |
| 4. MCP + Agent | MCP 서버, 단일 Agent 증거 매핑, 구조화 출력, `DRAFT` 검토·이력 | Claude Code에서 평가 실행·저장, 미확인 사실 구분 |
| 5. UI + 문서 | 한국어 대시보드·지원 현황, 증거 기반 이력서·자기소개서 초안 | 평가부터 초안 작성까지 한 흐름으로 수행 |
| 6. 벤치마크 | 추출 안정성, 증거 정확도, 근거 없는 주장, Eligibility 오류, 재현성, 지연·토큰 측정. LLM 단독 vs 증거 기반 비교 후 멀티에이전트 실험 | 실험 결과 문서화, 아키텍처 선택을 데이터로 설명 |

**개발 원칙**: 작고 테스트 가능한 단위로 구현한다. 수정 전에 확인하고, 코드와 함께 테스트를 작성하며, 실제 결과와 한계를 보고한다. 불필요한 통합이나 프레임워크를 들이지 않는다.

# 14. 성공 기준

- [ ] 실제 채용공고가 예약된 작업으로 자동 수집된다.
- [ ] 서로 다른 출처의 같은 공고를 중복 관리하지 않는다.
- [ ] 필수·우대 조건을 구분하고 Eligibility를 판정한다.
- [ ] 실제 프로젝트·논문·경력 증거가 버전과 함께 DB에 저장된다.
- [ ] AI Agent가 MCP로 공고와 증거를 조회한다.
- [ ] 요구사항과 증거 버전의 연결 관계를 확인할 수 있다.
- [ ] Fit Score가 결정론적으로 계산되고 점수 범위와 Coverage가 함께 제시된다.
- [ ] Global Opportunity Score가 별도로 제시된다.
- [ ] 평가 실행과 변경 이력을 추적할 수 있다.
- [ ] 웹 대시보드에서 공고와 지원 상태를 관리할 수 있다.
- [ ] 검증 가능한 경험만으로 이력서·자기소개서 초안을 만들고, 주장–증거 연결을 확인할 수 있다.
- [ ] 핵심 기능의 자동화 테스트가 통과한다.
- [ ] 개발 과정과 평가 결과를 README와 기술 문서로 설명할 수 있다.

# 15. 차별점

1. **한국 채용시장 중심의 자동 발견**: 신입·인턴·채용연계형을 고려하고, 공식 API·ATS·RSS·알림 메일을 겹쳐 공고를 찾는 노동을 없앤다.
2. **증거 기반 평가**: LLM에게 적합성을 묻는 대신, 요구사항과 실제 경험의 근거 관계를 버전 관리되는 데이터로 다룬다.
3. **세 가지 독립 결과**: 지원 자격, 요구사항 일치도, 지원 가치를 서로 섞지 않는다.
4. **역할이 분명한 Agent와 MCP**: Agent는 탐색과 해석, MCP는 도구 접근, Backend는 데이터와 결정론적 로직을 맡는다.
5. **AI 시스템 자체의 품질 측정**: 정확도, 재현성, 비용, 지연, 멀티에이전트 효과를 측정해 설계의 타당성을 검증한다.

# 16. 최종 비전

Proofit의 목표는 많은 공고를 보여 주는 것이 아니라, **지원자의 실제 경험을 이해하고, 지원할 가치가 있는 기회를 찾고, 그 판단을 검증 가능한 근거로 설명하는 개인용 AI Career Copilot**을 만드는 것이다.

프로젝트의 성공은 사용한 AI 기술의 개수가 아니라 **자동 수집의 안정성, 평가의 정확성과 재현성, 의사결정에 주는 실질적인 가치**로 판단한다.
