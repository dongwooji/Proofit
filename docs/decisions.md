- **이유**: 혼자 하는 프로젝트에서 기능마다 생기는 문서(spec·plan·tasks)의 관리 부담이 크고, 기획서와 내용이 겹친다.

## 채용공고 수집

### D-010. 자동 발견이 핵심, 수동 등록은 대체 수단 — `채택`
- **결정**: 공고를 찾는 노동을 없애는 것이 프로젝트의 목적이다. 수동 URL 등록·본문 붙여넣기는 자동 경로가 놓친 공고를 위한 **fallback**으로만 둔다.
- **이유**: 수동 등록을 주 경로로 두면 사용자가 공고를 직접 찾아야 해서 자동화 목적과 맞지 않는다.

### D-011. 수집 경로와 우선순위 — `채택`
- **결정**: 아래 Provider 유형을 겹쳐서 커버리지를 확보한다.
  1. **공식 API** (`ApiProvider`): 로켓펀치 → 사람인·고용24(신청 후 승인) → 원티드(신청해 봄)
  2. **공개 ATS Job Board API** (`AtsBoardProvider`): Greenhouse, Lever, Ashby. 관심 기업 목록을 한 번 등록
  3. **공식 RSS** (`FeedProvider`): 인디스워크 등
  4. **채용 알림 메일** (`EmailAlertProvider`): 잡코리아·캐치·LinkedIn 등에서 맞춤 알림을 한 번 설정하고, 읽기 전용 메일 접근으로 수집
- **이유**: 출처 하나로는 대기업 공채, 스타트업, 외국계를 모두 덮을 수 없다. 처음 설정 이후에는 사용자가 할 일이 없다.
- **비고**: 각 사이트가 실제로 알림 메일을 보내는지, 메일에 어떤 정보가 담기는지는 구현 전에 확인한다.

### D-012. 채용 플랫폼 크롤링 금지 — `채택`
- **결정**: 이용약관이나 robots.txt가 자동 수집을 금지하는 채용 플랫폼(잡코리아, 캐치, 인크루트 등)을 크롤링하지 않는다. 로그인·접근 제한·CAPTCHA·봇 차단을 우회하지 않는다.
- **이유**: 약관 위반과 법적 위험. 포트폴리오로 공개할 때 수집 정책을 명확히 설명할 수 있어야 한다.

### D-013. Google Alerts 미사용 — `채택`
- **결정**: Google Alerts를 수집 경로로 쓰지 않는다.
- **이유**: 검토 결과 결과 누락이 잦고, 색인 지연이 있으며, 실제 공고보다 채용 뉴스·블로그 같은 잡음이 많다. 공채 시즌 감지 같은 보조 용도는 가능했지만 사용자 결정으로 제외했다.

### D-014. 발견과 상세 보강 분리 — `채택`
- **결정**: 공고를 **목록 메타데이터(listing)**와 **검증된 상세 JD**로 나눠 저장한다(`detail_status`). 상세 JD 확보 방식은 출처별 약관을 확인한 뒤 정한다.
- **이유**: 알림 메일 같은 출처는 제목·회사·링크만 준다. 발견 자체는 자동으로 하고, 평가에 필요한 본문은 필터를 통과한 공고에만 확보한다.

### D-015. 첫 자동 수집 출처는 로켓펀치 — `채택`
- **결정**: MVP의 "실제로 자동 동작하는 출처 1개"는 로켓펀치 Open API로 시작한다.
- **이유**: 조사한 출처 중 유일하게 별도 승인 없이 개발자 콘솔에서 키가 바로 발급된다.

## 평가

### D-020. 평가 결과를 세 가지로 분리 — `채택`
- **결정**: **Eligibility**(ELIGIBLE/INELIGIBLE/UNCERTAIN), **Evidence-based Fit Score**(0~100), **Global Opportunity Score**(1~5)를 서로 독립적으로 산출하고, 서로 덮어쓰거나 조정하지 않는다.
- **이유**: "지원할 수 있는가", "요구사항과 얼마나 맞는가", "지원할 가치가 있는가"는 다른 질문이다. 섞으면 점수의 의미를 설명할 수 없다.

### D-021. 필수/우대와 중요도는 별개의 축 — `채택`
- **결정**: 요구사항마다 필수/우대(Eligibility용)와 High/Medium/Low 중요도(Fit Score 가중치)를 따로 판정한다. 중요도는 공고 표현으로만 정하고 지원자 역량에 따라 바꾸지 않는다.

### D-022. Knockout 규칙 — `채택`
- **결정**: 필수 요건이 **미충족으로 확인된 경우에만** `INELIGIBLE`. 증거가 없을 뿐이면 `UNCERTAIN`(확인 필요). Eligibility는 추천을 거르는 데만 쓰고 **Fit Score를 바꾸지 않는다.**
- **이유**: 가중 평균만 쓰면 필수 요건을 못 채워도 높은 점수가 나올 수 있다. 반대로 점수를 깎는 방식은 Fit Score의 의미를 흐린다.
- **비고**: 검토 초기에는 "필수 미충족 시 점수 상한"도 고려했지만, 점수와 자격을 분리하는 쪽으로 정했다.

### D-023. Unknown 처리, 점수 범위, 반올림 — `채택`
- **결정**:
  - Unknown은 None과 구분해 저장한다.
  - **하한** = Unknown을 0으로, **상한** = Unknown을 1.0으로 계산하고 **Evidence Coverage**와 함께 보고한다.
  - `Decimal`로 계산하고 소수 첫째 자리에서 ROUND_HALF_UP.
- **이유**: 같은 입력이면 같은 점수가 나와야 한다는 원칙을 반올림까지 포함해 보장하기 위해서다.
- **미정**: "증거 확인 필요"로 표시할 Coverage 기준값 → 평가 데이터셋으로 정한다.

### D-024. 증거 강도 판정 기준(rubric) — `채택`
- **결정**: Strong = 직접 수행이 확인됨 / Partial = 관련 경험은 있지만 요구 범위·깊이 부족 / None = 검토한 자료에 근거 없음 / Unknown = 판단 자료 부족.
- **이유**: 기준이 없으면 LLM과 라벨링하는 사람 모두 판정이 흔들린다.

### D-025. 요구사항 세트를 스냅샷 단위로 고정 — `채택`
- **결정**: 요구사항 추출은 공고 스냅샷당 한 번 하고 승인된 세트를 재사용한다. JD가 바뀌거나 추출을 명시적으로 수정할 때만 새 버전을 만든다.
- **이유**: 평가할 때마다 LLM이 요구사항을 다르게 쪼개면 분모가 바뀌어 점수가 흔들린다. 결정론적 계산만으로는 재현성이 보장되지 않는다.

### D-026. Global Opportunity Score의 미확인 정보 — `채택`
- **결정**: 보상·근무조건 등 공고에 없는 정보는 '미확인'으로 표시하고 지어내지 않는다. 어떤 점수도 합격 확률이 아니다.

## 데이터 모델

### D-030. 증거 버전 관리 — `채택`
- **결정**: `evidence_items`와 `evidence_item_versions`를 분리하고, 평가·문서는 증거의 **특정 버전**을 참조한다.
- **이유**: 증거를 수정해도 과거 평가 당시의 판정을 복원할 수 있어야 한다.

### D-031. 보완된 테이블 — `채택`
- **결정**: `requirement_sets`(스냅샷별 요구사항 세트), `duplicate_candidates`(사용자 확인용 중복 의심 쌍), `document_claims`(문서 주장 ↔ 증거 버전), `scoring_policies`(가중치·기준·반올림, 버전·해시), `collection_sources`(출처 설정)를 추가한다. Eligibility는 `evaluations`에 저장한다.

### D-032. 공고 상태와 지원 상태 분리 — `채택`
- **결정**:
  - `job.status`: `OPEN` 진행 / `CLOSED` 마감 / `UNKNOWN` 미확인
  - `application.status`: `REVIEWING` 검토 / `PLANNED` 지원 예정 / `APPLIED` 지원 / `ASSESSMENT` 시험 / `INTERVIEW` 면접 / `OFFER` 합격 / `REJECTED` 불합격 / `WITHDRAWN` 철회 / `SKIPPED` 건너뜀
  - 모든 지원 상태 변경은 이벤트로 기록한다.
- **이유**: 공고 마감은 지원 결과가 아니다. "지원하지 않기로 한 공고"도 기록해야 판단 이력이 남는다.

### D-033. 마감일 유형 — `채택`
- **결정**: `deadline_type`으로 날짜 / 상시채용 / 채용 시 마감을 구분한다.

### D-034. SQLite WAL + Alembic — `채택`
- **결정**: FastAPI와 MCP 서버가 같은 DB를 쓰므로 SQLite를 WAL 모드로 쓰고, 스키마 변경은 Alembic으로 관리한다.

## 아키텍처 · AI

### D-040. 공통 서비스 계층 — `채택`
- **결정**: FastAPI와 MCP 서버는 같은 서비스 계층을 호출한다. 검증·수집·중복 제거·점수 계산·저장 로직을 중복 구현하지 않는다.
- **이유**: 두 진입점에 로직이 따로 있으면 규칙이 어긋난다.

### D-041. MCP 설계 — `채택`
- **결정**: Tool·Resource·Prompt를 모두 사용한다. 읽기·쓰기 권한을 분리하고, 쓰기 도구에는 스키마 검증·idempotency key·감사 로그를 둔다. 평가에 불필요한 개인정보(연락처 등)는 MCP 응답에서 제외한다.
- **이유**: MCP는 이 구조에서 원래 필요한 인터페이스이고, 깊이 있게 설계하는 것 자체가 학습 목표다.

### D-042. AI 결과는 DRAFT로 시작 — `채택`
- **결정**: AI가 저장한 평가·문서는 `DRAFT`이고, 사용자가 대시보드에서 확정한다. 확정해도 이력을 덮어쓰지 않는다.

### D-043. 프롬프트·모델 버전 기록 — `채택`
- **결정**: 평가 워크플로를 Claude Code skill 파일로 관리하고 **파일 해시**를 프롬프트 버전으로 기록한다. 모델 정보는 Agent가 **보고한 값**으로 기록하며 검증된 값이 아님을 명시한다.
- **이유**: MCP 서버는 호출한 모델을 직접 알 수 없다.

### D-044. AI 실행·비용 정책 — `채택`
- **결정**: MVP는 사용자가 Claude Code에서 Agent를 직접 실행한다. 수집·정규화·중복 제거는 LLM 없이 동작한다. Claude Code 구독을 무인 백엔드 인증 수단으로 쓰지 않는다. 무인 AI 평가가 필요하면 별도 API·비용 한도를 설계한다.

### D-045. 멀티에이전트는 Verification 중심 통제 실험 — `채택`
- **결정**: MVP는 단일 Agent. 이후 같은 평가셋에서 ① 단일 ② 단일 + 자기 검토 ③ 단일 + 독립 맥락 검증 Agent ④ 전체 분리를 비교하고, 개선이 확인될 때만 도입한다. 먼저 Claude Code 서브에이전트로 실험하고, 이후 Agent SDK/API로 오케스트레이션을 직접 구현한다.
- **이유**: 공고 한 건 평가는 단일 Agent로 충분할 가능성이 높다. ②와 ③의 차이가 "에이전트를 나눈 효과"이고, ②가 없으면 효과의 원인을 구분할 수 없다.

### D-046. 기준선: LLM 단독 평가 vs 증거 기반 평가 — `채택`
- **결정**: LLM에게 종합 점수만 묻는 방식을 기준선으로 두고, 사용자의 실제 판단(지원 여부, 서류 결과)과의 일치도를 비교한다.
- **이유**: "증거 기반 평가가 더 낫다"는 주장을 데이터로 뒷받침하기 위해서다.

## 참고: 채용 데이터 출처 조사 (2026-11-21 기준)

공식 페이지와 문서 기준으로 조사했다. 조건은 바뀔 수 있으므로 연동 전에 다시 확인한다.

| 출처 | 공식 API | 개인 이용 | 확인된 조건 |
|---|---|---|---|
| 로켓펀치 | 있음 (Open API) | 가능 (콘솔에서 즉시 발급, 별도 승인 없음) | App Key(`X-RP-API-Key` 헤더), 분당 60회·일 5,000회, 키는 서버에서만 사용 |
| 사람인 | 있음 (`oapi.saramin.co.kr`) | 신청 후 승인 (개인 가능 여부 명시 없음) | 하루 공고 호출 최대 500건, "Powered by 취업 사람인" 출처 표시 의무, 재판매·이용요금 부과 금지, 키 공유 금지 |
| 고용24 (구 워크넷) | 있음 (OPEN-API 메뉴) | 가능성 높음 (미확인) | 조사 당시 신청 페이지 접속 오류(503)로 조건 미확인 |
| 원티드 | 있음 (`openapi.wanted.jobs`) | 불확실 (신청서에 회사명 필수) | 신청 후 3영업일 내 키 메일 발송, 한도·약관 미확인 |
| 잡코리아 | 있음 | 사실상 어려움 | 공공기관·학교 우선, 개인·일반 기업은 내부 검토 후 거절 가능 |
| 랠릿 | 있음 | 불가 (파트너 전용) | 랠릿이 파트너사에 키를 사전 제공 |
